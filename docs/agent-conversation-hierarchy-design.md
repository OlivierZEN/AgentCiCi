# 智能体-会话层次设计文档

更新时间：2026-04-16  
适用范围：`frontend/assistant workspace`、后续 `backend` 会话域建模

## 1. 设计背景

当前项目原先更接近“直接展示会话列表”的 IM 视图，这对单一助手场景是够用的，但当系统开始支持多个已发布智能体、多渠道接入和内置标准智能体后，顶层对象就不应该再是“渠道”或“混合会话列表”，而应当升级为：

**智能体 -> 会话 -> 消息**

这个层次对应用户已经形成的稳定心智模型：

- 一个已发布智能体，相当于一个顶层项目或工作区
- 智能体下面挂很多独立会话
- 每条会话可以来自不同渠道
- 每条消息永远只属于某一条会话

## 2. 核心术语

### 2.1 Agent

系统中一个可发布、可选择、可治理的智能体定义。

示例：

- 思思（CiCi）- 系统内置标准智能体
- 售前跟进 Agent
- 审批推进 Agent

### 2.2 Conversation

某个参与方与某个智能体之间的一段持续对话线程。

示例：

- 企微里的 `张经理`
- 钉钉里的 `王主管`
- 飞书里的 `客户咨询群`
- WebChat 里的 `官网访客 1024`

### 2.3 Message

会话中的逐条消息收发记录，包括用户消息、助手消息、工具结果、系统事件等。

### 2.4 Channel

会话来源渠道，是会话的属性，不再是顶层业务对象。

示例：

- `wechat`
- `dingtalk`
- `feishu`
- `webchat`

### 2.5 Participant

会话对端实体，可能是：

- 单个外部客户
- 内部员工
- 群聊/群组
- 匿名访客

## 3. 顶层信息架构

新的助手端工作台建议按下面的层次组织：

1. 左侧图标栏：全局工作台入口
2. 智能体目录：展示系统内置智能体与已发布智能体
3. 会话线程列表：只展示当前选中智能体下的会话
4. 聊天主区：展示当前会话的消息流
5. 右侧上下文区：展示当前智能体、会话对象、知识策略和快捷动作

其中最关键的结构原则是：

- 顶层选择的是 `Agent`
- 渠道筛选发生在 `Conversation` 列表层
- `Message` 只在聊天主区出现

## 4. 产品规则

### 4.1 系统内置智能体

`思思（CiCi）` 是系统内置标准智能体，满足以下规则：

- 常驻智能体列表
- 默认可见
- 默认在线
- 不应被普通用户删除
- 可作为多渠道统一兜底入口

建议字段：

- `agent.type = system`
- `agent.builtin = true`
- `agent.status = active`
- `agent.pinned = true`

### 4.2 已发布智能体

每个已发布智能体在 UI 上都应是一个一级对象，拥有自己的：

- 名称
- 简介
- 支持渠道
- 已关联会话数
- 状态
- 知识策略/工具策略

### 4.3 渠道不再作为顶层对象

`企微 / 钉钉 / 飞书 / WebChat` 应保留为：

- 会话来源属性
- 会话列表筛选项
- 统计维度

而不是取代智能体成为工作台顶层实体。

## 5. 建议数据模型

### 5.1 Agent

建议核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 智能体 ID |
| `name` | 智能体名称 |
| `type` | `system` / `published` / `draft` |
| `status` | `active` / `paused` / `archived` |
| `builtin` | 是否系统内置 |
| `summary` | 简介 |
| `channel_caps` | 支持的渠道集合 |
| `knowledge_policy` | 关联知识策略 |
| `tool_policy` | 关联工具策略 |

### 5.2 Conversation

建议核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 会话 ID |
| `agent_id` | 所属智能体 |
| `channel` | 来源渠道 |
| `participant_id` | 对端 ID |
| `participant_type` | `employee` / `external` / `group` / `anonymous` |
| `title` | 会话标题 |
| `owner_user_id` | 当前负责人 |
| `status` | `open` / `closed` / `handoff` |
| `last_message_at` | 最后消息时间 |
| `unread_count` | 未读数 |

### 5.3 Message

建议核心字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 消息 ID |
| `conversation_id` | 所属会话 |
| `role` | `user` / `assistant` / `tool` / `system` |
| `content` | 消息正文 |
| `channel_message_id` | 渠道侧消息 ID |
| `created_at` | 创建时间 |
| `metadata` | 工具、知识命中、审核等扩展信息 |

## 6. 前端落地原则

### 6.1 这次迭代的目标

本次对当前项目的调整目标不是一次性打穿全部后端建模，而是先把助手端工作台的视图结构和前端状态模型调整到正确方向：

- 在前端把顶层对象改成智能体
- 会话列表按当前选中智能体过滤
- 渠道退为会话筛选条件
- 聊天头部和右侧信息区同时展示“当前智能体”和“当前会话对象”

### 6.2 当前实现方式

当前前端用静态样例数据表达：

- 智能体目录
- 智能体下的会话线程
- 每条线程的初始消息

这样可以先稳定交互与视觉结构，再逐步把真实后端数据接进来。

## 7. 后端后续建议

后续后端演进应从“通用 chat session”进一步细化到“agent-scoped conversation”：

1. `conversation` 必须显式带 `agent_id`
2. `channel` 下沉到会话维度
3. 查询会话列表时支持按 `agent_id`、`channel`、`participant` 过滤
4. 内置 CiCi 作为种子智能体写入基础数据
5. 聊天接口入参逐步从“仅 sessionId”扩展为“agentId + conversationId”

## 8. 本次项目调整结论

本次调整后，当前项目的助手端已经在前端层面体现了这套结构：

- `Agent` 是左侧一级对象
- `Conversation` 是智能体下的线程列表
- `Message` 在聊天主区展示
- `Channel` 作为会话筛选与标记出现
- `CiCi` 作为系统内置标准智能体常驻列表

这为后续把真实微信、钉钉、飞书和 WebChat 渠道会话接进系统，提供了更稳定的产品骨架。
