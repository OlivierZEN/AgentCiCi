# FEAT-192 - DevAutopilot 产品经理结构化语义判定与标准输出

## 背景与根因

UAT 的产品经理对“创建一个项目：CCSales智能应用”没有调用写工具，最终被可信回执门禁替换为未写入提示；切换固定模型后，本地仍可复现。进一步验证表明故障不是单纯的模型智力问题，而是编排层在模型前后使用不完备的文本规则：

- 创建草案和事实查询在调用模型前按关键词分流；“帮我建一个项目”未命中创建分支，却因“项目”命中只读查询。
- 转派草案由正则从自然语言提取开发者名称。
- 回执门禁先按用户问题中的写入词和对象词判断是否启用，导致不同表达可能绕过同一安全边界。
- 草案正文由模型自由生成；即使语义判断一致，标题、字段顺序和确认口令也可能变化，模型曾输出服务端不接受的无冒号确认文本。
- 模型遗漏结构化标记时，旧逻辑会再用关键词和 Markdown 正则从可见文本反推业务字段，既不完备也不能证明字段来自同一结构化决策。
- 首轮改造在思考模式模型上强制命名 `tool_choice`；百炼会在模型推理前拒绝该组合，Trace 表现为 0 input/output Token，与模型语义能力无关。
- 已明确描述“产品/项目 + 页面位置 + 界面元素 + 修改方向”的 UI 需求，曾被结构化判定为需求后因 `title` 或 `pm_assessment` 未完整返回而退化成“请说明业务结果”的泛化澄清；第二轮普通对话才能依据上下文问到图标来源、是否保留文字和期望效果。根因是结构化字段说明与不完整草案回退都丢失了已知上下文，不是用户缺少最基本的业务意图。
- 项目修改草案曾输出 `确认将项目 <编号> 的名称修改为 <新值>`，但后端旧解析器只识别 `确认修改项目：...`，且阻塞/流式编排与 Tool dispatcher 都没有 update 确定性通道；旧 Tool 回执又缺少写后查询和统一可信字段，导致确认后显示“内部字段已隐藏”，实时查询仍是旧值和旧 revision。

## 设计原则

1. 在输入不是产品定义的固定协议时，禁止使用关键词、正则或固定词位判断用户真实意图。
2. 当前选定模型结合完整当前消息和最近会话，输出受 JSON Schema 约束的函数调用；服务端只校验结构化字段，不解析模型自然语言正文。
3. 只有系统明确公布的确认协议继续使用确定性解析，例如 `确认创建项目：<名称>`、`确认删除任务：<记录>` 和任务转派确认。
4. 模型只负责语义与业务字段，服务端负责权限、确认、Tool 执行、可信回执和用户可见格式。
5. 明确判定统一使用固定模板；低置信度或关键字段缺失统一进入单问题澄清，不执行查询或写入。
6. 结构化判定不可用时固定失败关闭；判定完成后，通用模型循环不再获得研发交付查询工具，避免第二次自由判断绕过该结果。
7. 澄清必须先复述已经识别的对象和修改方向，再只询问影响验收的产品选择，并在可安全默认时给出默认处理方式；不得让用户重复已经说清楚的业务结果。界面改动中的图标来源/样式、是否保留文字和完成后的可见效果属于可聚焦的产品选择，不应退化成抽象技术追问。
8. 修改确认必须是自包含、精确且服务端公布的协议；服务端只解析对象类型、记录引用、允许字段和目标值，不用正则推断普通自然语言意图。确认后的更新 Tool 不向自由模型开放，只能由确定性路由执行。

## 结构化判定契约

模型必须调用唯一函数 `resolve_devautopilot_dialogue`，调用固定为 `temperature=0`、禁用并行 Tool。首轮使用思考模式兼容的唯一工具 `auto` 选择并严格验证返回；若未返回唯一目标函数，则关闭思考模式做一次命名工具协议重试，仍失败则关闭本轮。结果包含：

- `action`：`CREATE_DRAFT`、`QUERY`、`DELETE_DRAFT`、`TRANSFER_DRAFT`、`CANCEL_DRAFT`、`OTHER`。
- `object_type`：项目、需求、任务、缺陷、变更、工时、交付事件或未知。
- `confidence`、简洁分类依据和一个可选澄清问题。
- 项目名称、父项目/父需求、标题，以及需求/缺陷/变更专业整理字段。
- 删除目标、转出/转入开发者等动作特定字段。
- `original_report` 与 `user_supplements` 必须逐字对应真实用户消息；服务端按会话原文校验，不接受模型补造。
- 只把动作核心字段设为全局必填；其余字段按 action/object_type 校验。PROJECT 中模型若把新项目名称放入结构化 `project` 字段，服务端可将其规范化为 `name`，不得据用户自然语言补抽取。
- `REQUIREMENT` 的 `title`、`classification_reason` 和 `pm_assessment` 由产品经理根据原始描述专业整理，不得因为用户没有使用正式需求标题或产品术语而留空。对于已给出页面位置、界面元素和修改方向的视觉需求，若图标来源/样式、文字保留方式等仍影响验收，则澄清必须复述已理解的改动、询问这些具体选择并提供遵循现有设计系统的默认方案。

模型必须按完整语义处理否定、假设、反问、指代、上下文补充和隐含请求。出现“创建项目”不等于创建意图；未出现“创建”也不等于没有创建意图。

## 标准输出

明确的创建草案、删除草案、转派草案、取消和澄清均由服务端渲染，固定包含：

- 稳定标题；
- 固定字段顺序；
- `当前状态` 与 `数据写入`；
- 唯一、可复制且与服务端解析器完全一致的确认文本。

项目草案固定为项目名称、初始状态、健康度、进度和版本；需求/缺陷/变更固定渲染专业整理，并由同一结构化对象生成不可见 `DEV_AUTOPILOT_INTAKE_V1` 标记。不得从缺少标记的自由文本草案恢复可执行写入。

## 可信回执边界

- 回执门禁不再读取用户文本判断意图。
- 回复只要声称研发交付写入已经完成，就必须在本轮 Trace 中存在允许的 Semattice 写 Tool、`SUCCESS / SEMATTICE_LIVE`、record ID、正 revision、correlation ID 和写后回读；创建还必须有内容摘要。
- 输出检测只用于识别回复是否声称完成，不用于推断用户意图；条件式或将来式草案不被拦截。
- 无结构化判定、无有效草案、低置信度、Tool 失败或回读不完整均失败关闭，不得伪造业务编号。
- 修改必须先精确匹配记录 ID、业务编号或完整名称/标题，使用当前 revision 乐观锁写入，再实时查询同一 record ID；目标字段值和 revision 未同时核对成功时不得返回成功。重复确认若回读已是目标值，应返回带可信回读的幂等 NOOP，不重复写入。

## 验收标准

- “创建项目：X”“帮我建一个项目：X”及不含创建关键词但整体语义明确的新增项目表达，都由模型结构化判定为项目草案并输出同一格式。
- 包含“创建项目”但整体语义是否定、举例、询问或历史故障讨论时，不生成创建草案。
- 创建草案始终输出 `确认创建项目：<名称>`，包含中文冒号，重复渲染字节级一致。
- 项目事实查询只在模型明确返回 `QUERY` 且置信度达到门槛时执行，不再因出现“项目”等词自动查询。
- 自然语言转派先由模型给出结构化人员，再执行只读草案 Tool；只有固定确认协议执行写入。
- 缺少不可见结构化标记的旧自由文本草案不能通过短确认写入。
- 回执门禁不依赖用户问题关键词，能够阻断隐含表达下的伪成功，并不误伤 CRM 等非研发交付答案。
- 阻塞与流式聊天使用同一判定、固定输出、确认和回执规则。
- “将某页面右上角的回收站按钮改成对应图标”一类输入不得返回“请再说明希望达到的业务结果”；若仍需澄清，应围绕图标来源/样式、是否保留按钮文字和默认设计规范给出上下文明确的单次追问。
- `确认将项目 DAS-4F5ED86B 的名称修改为 AgentCiCi企业级智能体平台` 由服务端直接执行；普通“帮我改名”、结构字段修改和不合法数值都不能触发写入。成功答复必须包含实际 record ID、正 revision 与关联号，失败或回读不一致必须明确说明未修改，不能显示受保护字段占位文案。

## 发布与回滚

- 本任务已进入 AgentCiCi 远程 `main` 并随 `2.8.61-beta.28 / 242074e72a9e` 完成 UAT 技术发布；真实已登录产品经理对话仍作为独立业务验收，生产未发布。
- 回滚应用镜像即可恢复旧编排；已成功写入的 Semattice 记录不随应用回滚删除。
- 可信回执完整性门禁不得因回滚降低。
