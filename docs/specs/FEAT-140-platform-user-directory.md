# FEAT-140 - 平台全量个人用户目录

## 背景与目标

运营管理端“注册用户”当前只显示没有任何组织成员关系的个人账户。运营人员无法在同一目录中检索已加入组织的个人用户，且页面说明与“全平台用户”治理诉求不符。

本次将该目录定义为平台全量个人账户视图：所有已注册的 `user_account` 都应显示，无论其是否已加入组织；同一人加入多个组织仍只显示一条账户记录。

## 范围

### In Scope

- 将 `GET /platform/registered-users` 的查询来源调整为全量 `user_account`。
- 保留昵称、手机号、邮箱检索，创建时间倒序和既有分页语义。
- 以全局账户 ID 为行主键，确保多组织成员关系不产生重复行。
- 更新平台页面说明、空态和可访问标签，使其准确表达“全平台个人用户”。
- 增加后端和前端定向回归，覆盖无组织账户、单组织账户、多组织账户与检索/分页。

### Out Of Scope

- 不展示组织名称、成员角色、组织数量或跨组织明细。
- 不修改用户注册、组织邀请、成员关系、权限边界、数据迁移或移动端布局。
- 已按用户明确授权发布生产；不扩展到其他用户或组织治理功能。

## 用户场景

- 平台运营人员进入“注册用户”，查看平台上所有个人账户。
- 一个账户加入零个、一个或多个组织时，均只以该账户的一行出现。
- 运营人员可按昵称、手机号或邮箱筛选，并保持分页总数与行数一致。

## 现状与约束

- 账号主数据为 `user_account`；`company_member` 只是账户与组织的成员关系，可一对多。
- 现有 `searchPersonalAccounts` 使用 `not exists company_member` 条件，因此错误排除了已加入组织的账户。
- 接口保持平台角色保护和现有响应形状，不向前端暴露组织成员数据。

## 方案设计

- 在 `UserAccountRepository` 提供按账户表搜索的查询，不联结成员表。
- `PlatformRegisteredUserService` 使用全量账户查询；每个结果实体即唯一的全局账户。
- 前端复用现有表格、搜索与分页控件，只将说明和空态改为全平台个人用户语义；不改变视觉结构或主题 token。

## 接口与数据影响

- `GET /platform/registered-users` 的路径、鉴权、参数和响应字段不变。
- 返回集合从“未加入组织账户”扩展为“全部个人账户”，这是有意的读取语义变更。
- 无数据库 schema 或写入行为变化；回滚可恢复旧查询条件。

## 验收标准

- 无组织、单组织和多组织账户均出现在同一列表中。
- 多组织账户在列表及 total 中只计一次。
- 昵称、手机号、邮箱检索和创建时间倒序仍正确，分页无重复或漏数。
- 平台角色保护不变，接口响应字段不变。
- 定向后端/前端测试、前端构建和 `git diff --check` 通过。

## 风险与回滚

- 列表总数会上升，运营端可见范围扩大但仍受既有平台角色保护。
- 若发现查询性能或展示回归，回滚本次变更可恢复旧的无成员过滤；本次不涉及数据迁移。

## 实现进展

- 已将目录查询改为只读取 `user_account` 的 `searchRegisteredAccounts`，不会联结 `company_member`。
- 服务、控制器和页面均已切换到全量个人账户语义，接口路径、鉴权、参数与响应字段不变。
- 后端定向测试、前端定向测试、生产构建与 diff 检查通过。
- 已合并 `main` 并发布 `2.8.15 / 38cb22e3a587`；发布前完整备份、六服务健康、版本/Nginx 和公网入口检查通过。
