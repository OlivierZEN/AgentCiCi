# FEAT-039 - AgentCiCi 帮助中心站点

## 背景与目标

AgentCiCi 已经形成用户工作台、组织管理后台、平台控制面、Open API、嵌入式会议纪要、微信客服、知识库、技能、模型、工具和运行观测等多条产品能力线。当前说明散落在 README、规格文档、页面文案和代码入口里，普通用户、组织管理员、平台运营人员和开发者都缺少一个稳定的在线帮助入口。

本功能规划独立帮助中心站点 `help.agentcici.com`，用于承载 AgentCiCi 的产品使用手册、管理员操作指南、开发者接入文档、场景方案、故障排查和更新说明。帮助中心不是营销官网，也不是内部开发文档镜像，而是面向真实使用者的产品文档站。

核心目标：

- 用户能按任务快速找到答案，例如“怎么让知识库参与回答”“怎么开始会议纪要”“为什么没有命中文档”。
- 管理员能按配置流程完成组织初始化、知识库发布、模型接入、技能配置、智能体发布、Open API Key 管理和运行日志排查。
- 开发者能清楚理解 Open API、嵌入式会议纪要 SDK、鉴权、错误码、限流和安全建议。
- 平台运营人员能找到平台技能、内置工具、租户生命周期和平台审计相关说明。
- 文档结构能随产品功能扩展持续维护，避免只做一次性静态页面。

## 范围

### In Scope

- 规划 `help.agentcici.com` 的整体信息架构、导航体系、页面模板和首批内容清单。
- 覆盖当前系统三类主要产品入口：
  - 用户工作台 `/`
  - 组织管理后台 `/admin/*`
  - 平台控制面 `/platform/*`
- 覆盖当前关键能力：
  - 登录、账号、组织与角色
  - 对话、会话、知识库选择、条件检索
  - 会议纪要、客户洞察、个人设置、个人记忆
  - 知识库、模型、工具、技能、智能体构建、集成应用、微信客服
  - 嵌入式智能应用、Open API、API Key、调用日志
  - 观测运维、成本用量、审计日志
  - 平台技能、内置工具、租户生命周期、网站注册线索和平台审计
- 定义 MVP 首批上线文档、后续扩展文档和验收标准。
- 定义帮助文档的统一写作模板和 URL slug 规则。
- 定义帮助中心与现有 `PRODUCT.md`、`DESIGN.md`、`DESIGN.json` 的设计关系。

### Out Of Scope

- 本规格不重写现有产品功能。
- 本规格不替代 `docs/specs/` 中面向研发和交付的功能规格。
- 本规格不建设公开社区、工单系统、在线客服系统或用户论坛。
- 本规格不建设完整开发者门户、OAuth 应用市场或客户自助注册体系。
- 本规格不把 `agentcici.com` 主站改造成帮助中心。

## 设计原则

帮助中心按 product register 处理。它服务真实任务，不做营销页。

- 信息架构优先按角色和任务组织，而不是按代码模块堆叠。
- 首页优先提供搜索、角色入口、热门任务和最新更新。
- 文档正文使用清晰标题、短段落、步骤列表、注意事项和相关链接。
- 每篇文档必须明确适用角色、适用入口、前置条件、操作步骤、结果验证和常见错误。
- 管理员和开发者文档需要明确权限、风险、审计和安全边界。
- 帮助中心视觉延续 `鎏金账房` 的产品气质，但比管理后台略放松：暖白底、墨色正文、香槟金结构线和选中态，不使用营销型大 hero、装饰渐变、玻璃拟态或大面积深色。

```text
├─ 嵌入式会议纪要 SDK
├─ iframe 接入
└─ 安全最佳实践
```

开发者文档必须明确：

- API Key 不等同于管理员 JWT。
- API Key 只允许调用绑定智能体。
- 完整 Key 只在创建或重新生成时显示一次。
- 推荐服务端持有 Key，浏览器直传 Key 代表接受暴露风险。
- 每次调用应保存 `requestId` 和 `traceId`，便于管理员在运行日志中排查。

- 文档迁移时保留 redirect。

## 搜索与导航要求

帮助中心必须支持：

- 全站搜索，覆盖标题、正文、别名和错误码。
- 左侧文档树，移动端收起为目录按钮。
- 正文右侧页内目录，移动端变为顶部下拉或折叠目录。
- 面包屑，帮助用户知道当前文档归属。
- “上一篇 / 下一篇”和相关文档推荐。
- 对常见错误码提供可搜索别名，例如 `401`、`403`、`429`、`agent_api_key_missing`。
- 对产品入口提供可复制路径，例如 `/admin/kb`、`/admin/agent-builder`、`/platform/audit`。

## 视觉与交互要求

帮助中心继承 AgentCiCi 产品设计基线：

- 使用暖白背景和墨色正文。
- 香槟金只用于链接 focus、当前导航、分隔线和重点结构，不做大面积装饰填充。
- 首页不使用营销 hero，不使用夸张指标卡和重复卡片网格。
- 文档正文最大行宽控制在 65 到 75 个英文字符对应的中文舒适阅读宽度。
- 代码块、API 示例、错误码和路径使用等宽字体。
- 移动端目录和搜索不能遮挡正文。
- 不在文档正文中使用会干扰复制的装饰符号。

如果后续实现为独立前端页面，必须遵守 `DESIGN.md` 的 Page Implementation Quality Workflow：本地运行、桌面和移动截图检查、修复后复测。

## 非功能要求

- SEO：允许搜索引擎收录公开帮助文档，鉴权文档不展示任何真实密钥、token、客户数据或内网地址。
- 性能：首屏优先加载搜索框、导航和正文，不因大型脚本阻塞阅读。
- 可维护性：文档内容与导航配置应结构化，便于后续从 Markdown 或 CMS 生成。
- 可访问性：搜索、导航、目录和代码复制按钮支持键盘访问和可见 focus。
- 国际化预留：首版以中文为主，URL slug 使用英文，为后续英文版保留空间。
- 版本标记：涉及功能还未上线或处于 UAT 的文档，需要标明“当前限制”或“计划中”。

## 实施阶段建议

### Phase 1 - 文档骨架与 MVP 内容

- 建立帮助中心导航结构。
- 完成 MVP 12 篇文档。
- 首页提供搜索入口、角色入口和常用任务入口。
- 不接入复杂 CMS，优先使用 Markdown 或轻量内容数据。

### Phase 2 - 开发者与管理员深水区

- 补齐 Open API 完整接口文档、错误码、调用限制和 SDK / iframe 接入说明。
- 补齐知识库、技能、智能体构建、模型、工具、运行日志的排障文档。
- 给关键操作补截图或短流程图。

### Phase 3 - 场景方案与更新机制

- 补齐售后 Agent、微信客服、CloudCC CRM、会议纪要、客户洞察等场景方案。
- 建立更新日志机制。
- 为版本变更、已知限制和废弃能力建立稳定文档页。

## 验收标准

- `help.agentcici.com` 的一级信息架构覆盖快速开始、用户工作台、管理后台、平台控制面、Open API 与嵌入、场景方案、故障排查、安全与权限、更新日志。
- 首页能让用户在 2 次点击内进入用户指南、管理员指南、开发者文档或故障排查。
- MVP 至少上线 12 篇首批文档，并覆盖登录、知识库、模型、技能、智能体构建、Open API、API Key、运行日志、微信客服和会议纪要。
- 每篇文档使用统一模板，包含适用角色、适用入口、前置条件、操作步骤、结果验证和常见错误。
- Open API 文档明确 API Key 安全边界、鉴权方式、Chat、Stream Chat、Health、错误码、限流和 `requestId` / `traceId` 排查方式。
- 故障排查文档至少覆盖登录、权限、知识库未命中、模型失败、技能发布失败、Open API 401 / 403 / 429、SSE 异常、微信客服回调失败、会议麦克风不可用。
- 帮助中心视觉不偏离 `鎏金账房` 产品基线，不使用营销页风格、玻璃拟态、装饰渐变或大面积深色。
- 移动端可阅读、可搜索、可打开目录，不出现横向溢出。

## 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 产品能力仍在快速演进 | 文档容易过期 | 每个功能文档标注适用版本和最后更新时间，变更功能时同步更新帮助文档 |
| 研发规格过于技术化 | 用户难以理解 | 帮助文档只提炼用户任务，不直接复制研发规格 |
| Open API 文档暴露敏感示例 | 造成安全误解 | 示例统一使用占位符，不展示真实 Key、token、客户数据 |
| 管理后台和平台控制面边界混淆 | 用户找错入口 | 首页按角色分流，文档模板固定展示适用入口 |
| 帮助中心做成营销站 | 降低查找效率 | 遵守 product register，首页优先搜索、任务入口和文档导航 |
