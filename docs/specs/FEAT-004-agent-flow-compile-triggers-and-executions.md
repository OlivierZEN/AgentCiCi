# FEAT-004 智能体流程编译结果页 — 触发器与执行记录改造设计

## 背景与目标

### 背景

- **编译结果（图 1）**当前以「流程图预览 / 编译摘要 / 流程代码 / Manifest / 试运行」为主，强调**静态产物**与**单次试运行**，缺少与**运行态**的衔接。
- **个人工作流（图 2）**在流程未发布时，已显式预留 **「触发器」** 与 **「最近执行记录」** 两块区域，并通过文案说明「发布后从 routine 同步」「可手动执行或等待调度」，形成**设计 → 发布 → 调度/执行 → 可观测**的闭环心智。

### 目标

- 在智能体流程的**编译/版本**语境下，补齐与个人工作流一致的**触发器配置入口**与**执行记录可观测性**（含空态与发布后行为说明）。
- 不破坏现有「图 / 摘要 / 代码 / Manifest / 试运行」能力；以**信息架构扩展 + 与 START 语义对齐**为主，避免用户在两套界面间「猜哪里看触发与历史」。

## 问题陈述

| 缺口 | 用户影响 |
|------|----------|
| 无触发器呈现 | 不知道本智能体版本会被**谁/何时/以何种事件**拉起；与图上的「接收用户输入」起点无法对应到真实入口（会话、IM、门户、定时、Webhook 等）。 |
| 无执行记录 | 无法在同一上下文内看到**最近成功/失败、耗时、触发来源**；试运行与真实调度/线上触发的结果割裂。 |
| 生命周期文案弱 | 「先编译一次」「还没有版本」与个人工作流中「发布后出现定时触发器」的引导不一致，易产生**编译了但不知怎么跑、跑了不知道去哪看**的断层。 |

## 范围

### In Scope（设计交付）

- 编译结果页（或同级「版本/发布」面板）的**信息架构**与**关键界面区块**设计（含空态、加载、错误态）。
- **触发器**与 **START / 接收用户输入** 在流程图上的**语义对齐规则**（展示层，不要求本规格实现后端）。
- **执行记录列表**的字段建议、筛选维度、与「试运行」的**关系说明**（同一执行模型 vs 分轨）。
- 与个人工作流**文案与行为对齐**的差异表（哪些复用、哪些因「智能体」而不同）。

### Out of Scope（本规格不展开实现）

- 具体前端组件库选型、接口路径、数据库表结构（可在实现阶段另开技术子任务或 ADR）。
- 触发器全量类型（如复杂事件编排）的完整产品定义；本规格以**与个人工作流已暴露能力对齐**为下限。

## 参考：个人工作流（图 2）可复用模式

1. **分区标题 + 右侧动作**  
   - 「触发器」区 + 说明「发布后会在这里看到定时/周期触发器」；右侧可放「发布后自动从 routine 同步」类说明或配置入口（按产品最终文案统一）。
2. **「最近执行记录」区 + 主 CTA**  
   - 「执行默认 routine」类按钮，引导在未发布前的**有限能力**（或禁用并解释），发布后**手动触发**与**调度触发**并列说明。
3. **统一空态话术**  
   - 明确「还没有执行记录，发布后可手动执行或等待调度触发」，与触发器区形成**因果链**。

## 方案设计

### 1. 信息架构：在「编译结果」内增加两条「运行态」主轴

建议在现有 Tab 行**同一层级**扩展（或增加二级分组），避免运行态 buried 在子页：

| 建议 Tab / 分组名 | 职责 | 与现有 Tab 关系 |
|-------------------|------|----------------|
| **流程图预览**（保留） | 静态拓扑 + 与触发语义弱提示（见下节 START） | 现有 |
| **触发与调度**（新增，或拆为「触发器」「调度」两子 Tab） | 列出/只读展示本版本关联的触发器（定时/周期、渠道绑定摘要等）；未发布时空态 + 发布后数据 | **新增** |
| **执行记录**（新增） | 最近 N 条执行、状态、来源、耗时；支持跳转详情（若平台已有执行详情页则外链） | **新增** |
| 编译摘要 / 流程代码 / Manifest / 试运行（保留） | 产物与单次验证 | 现有；**试运行**在文案上与「执行记录」区分（见 3） |

**原则**：图看结构，**触发与调度**看入口，**执行记录**看历史；三者通过同一「版本上下文」串联。

### 2. START 节点与触发器的展示对齐（图 1 增强）

在流程图预览中，**不替代**独立「触发与调度」页，仅做**摘要徽章**：

- **START「接收用户输入」**旁展示：`已绑定渠道：会话 / IM / 门户`（示例）或「未绑定」灰态；若存在定时触发，显示 `定时 ×1` 等聚合标签。
- 点击 START 或徽章：**打开侧栏或浮层**，摘要触发器列表，主配置仍引导至「触发与调度」Tab。

这样解决「图上有起点但不知道真实触发从哪来」的认知问题。

### 3. 试运行 vs 执行记录

需在设计上二选一或组合（实现阶段定稿）：

- **方案 A（推荐）**：试运行产生的执行也写入**同一执行记录流**，带 `source=try_run` 标签；列表默认展示全部，可筛「仅生产触发」。
- **方案 B**：试运行仅本地会话，不进入记录；则须在试运行按钮旁**明确说明**，避免用户以为「跑过即会有历史」。

本规格倾向 **方案 A**，与个人工作流「一次执行一条记录」心智一致。

### 4. 生命周期与空态（对齐图 2）

| 阶段 | 触发器区 | 执行记录区 |
|------|----------|------------|
| 无版本 / 未编译 | 引导「先完成编译」；与个人工作流顶部「还没有版本，先编译一次」一致 | 空态：「编译后可试运行；发布后可见调度与手动执行记录」 |
| 已编译未发布 | 说明「发布后从 routine/发布管道同步定时触发器」；可展示**预期**类型（只读 Spec 若存在） | 「执行默认 routine」若可用则启用，否则禁用 + Tooltip 解释 |
| 已发布 | 展示真实触发器列表（与个人工作流一致） | 展示最近执行 + 筛选 |

### 5. 执行记录列表 — 最小字段集（建议）

- **执行 ID**、**开始/结束时间**、**状态**（成功/失败/运行中/取消）
- **触发来源**（手动 / 定时 / 渠道事件 / 试运行）
- **关联版本**或 **artifact 版本号**（与当前查看版本高亮一致）
- **耗时**、**失败原因摘要**（可折叠）

详情页：若已有统一「执行详情」，本页仅列表 + 跳转；若无，可在后续 FEAT 中定义 Trace/步骤级视图。

## 接口与数据影响（设计层假设）

- 需要**版本维度**查询：`agent_flow_version_id`（或等价物）下挂触发器列表与执行记录分页接口。
- 触发器数据可能来自**发布同步**（与个人工作流「发布后自动从 routine」一致），前端以**只读列表 + 跳转配置源**为主；是否在智能体侧支持编辑触发器属产品策略，本规格建议**一期只读对齐个人工作流**。

## 与个人工作流的差异（需产品确认）

| 维度 | 个人工作流 | 智能体流程 |
|------|------------|------------|
| 入口命名 | routine / 默认 routine | 是否沿用「routine」或改为「默认对话流 / 入口」需统一品牌文案 |
| 渠道 | 可能较简单 | 图 1 已强调会话、IM、门户；触发器摘要应覆盖 |
| 试运行 | 视现有产品 | 与执行记录是否合并（见 §3） |

## 验收标准（设计完成度）

- 能提供**线框级说明**或**Tab 结构表**给设计/前端，且无「触发器只存在于个人工作流、智能体编译页找不到」的断层。
- 明确 **3 个用户故事** 的可验收路径：
  1. 用户编译后能在**同一页**知道「何时会有定时触发器」。
  2. 用户发布后能在**同一页**看到触发器列表与最近执行。
  3. 用户在流程图上能**从 START 理解**入口与触发摘要，并跳到详情 Tab。

## 风险与回滚

- **风险**：若后端暂无版本级触发器/执行 API，UI 只能空态占位 → 需**功能开关**或与图 2 一致的诚实空态，避免假数据。
- **回滚**：新增 Tab 可独立开关；START 徽章为纯展示增强，关闭不影响核心编译视图。

- **数据库**：`V23__agent_workflow_execution_log.sql` → 表 `agent_workflow_execution_log`。

  - **触发与调度** / **执行记录** 优先展示后端接口数据；失败时回退/提示错误；支持「刷新列表」。
